Když Next.js představil App Router se Server Components, vypadalo to jako revoluční řešení mnoha problémů SPA. Lepší SEO, rychlejší načítání a příslib efektivnějšího vývoje. S touto technologií pracuji od jejího uvedení a chci se podělit o své upřímné zkušenosti – o to dobré i o to frustrující.

Původní příslib

Zdálo se, že App Router a jeho Server Components řeší zásadní problémy, které single page aplikace trápí už léta:

  • SEO – stránky přicházejí vykreslené na serveru, stejně jako už s Pages Routerem, a jsou připravené pro vyhledávače bez dalšího nastavování
  • Problémy s výkonem – menší bundly a rychlejší první načtení
  • Složitost načítání dat – jednodušší tok dat díky načítání na serveru

V příkladech typu Hello World to vypadalo fantasticky. Oddělení serverového a klientského kódu působilo čistě a logicky. Produkční aplikace ale vyprávějí jiný příběh.

Střet s realitou

Složitost autentizace

Jednou z prvních velkých překážek, na které narazíte, je autentizace. U klasických SPA spravujete stav session na jednom místě – na klientovi. Se Server Components musíte session řešit na serveru i na klientovi. Tahle duplicita není jen nepohodlná, je to zdroj chyb a nekonzistencí. 

// Server-side session handling
async function getServerSession() {
  // Server-side session logic
}

// Client-side session handling
function useClientSession() {
  // Client-side session logic
}

// Now you need to keep these in sync...

Mentální zátěž

Z každého rozhodnutí o komponentě se stává složitá otázka:

  • Má to být serverová, nebo klientská komponenta?
  • Kde mám tato data načíst – na serveru, na klientovi, nebo na obou?
  • Jak spolu budou tyto komponenty spolupracovat?
  • Co když v serverové komponentě potřebuji interaktivitu na straně klienta?

Tohle neustálé rozhodování představuje značnou kognitivní zátěž. Místo aby se vývojáři soustředili na business logiku, tráví čas navrhováním hranice mezi serverovým a klientským kódem.

Stavy načítání a streaming

Streamování dat zní teoreticky skvěle, ale implementovat praktické stavy načítání je překvapivě složité:

  • Načítání na úrovni stránky – příliš hrubé pro dobré UX
  • Hranice Suspense – fungují pro bloky komponent, ale co jemnější stavy načítání?
  • Částečné vykreslování – zobrazit statický obsah, zatímco se načítají dynamické části, se streamingem jde, ale každá dynamická část potřebuje vlastní hranici a fallback

Nakonec vytváříte specializované komponenty pro každý drobný kousek, který potřebuje vlastní obsluhu načítání. Z jednoduchosti rychle nic nezbude.

Složitost, kterou ušetříte na jednom místě, se často vynoří jinde – někdy v horší podobě.

Širší souvislosti

Tahle zkušenost se Server Components v Next.js odráží širší trend ve frontendovém vývoji, který mě znepokojuje. Místo abychom využívali nativní schopnosti prohlížeče a zjednodušovali si vývoj, přidáváme další vrstvy abstrakce, ve kterých se bez rozsáhlých mentálních modelů nedá vyznat.

Webový vývoj by se měl postupem času zjednodušovat. Prohlížeče toho zvládnou víc než kdy dřív – mají nativní moduly, lepší API a vyšší výkon. Přesto dál stavíme frameworky, které tato vylepšení schovávají za abstrakce a vytvářejí novou složitost.

Co to znamená pro vývojáře

Netvrdím, že jsou Server Components samy o sobě špatné – řeší skutečné problémy a ve správném kontextu můžou být přínosné. Propast mezi marketingovými sliby a realitou v produkci je ale značná.

Než nasadíte jakoukoli novou technologii, zvlášť takovou, která zásadně mění architekturu vaší aplikace, zvažte:

  • Řešíte skutečný problém, nebo se ženete za hypem?
  • Kolik bude stát dlouhodobá údržba?
  • Jak to ovlivní produktivitu vašeho týmu?
  • Nedosáhli byste stejných cílů jednodušším řešením?

Co dál

Tahle zkušenost mě inspirovala k tomu, abych začal víc sdílet upřímné pohledy na moderní webové technologie. V naší komunitě je příliš mnoho hypu a málo kritické analýzy.

V dalších článcích chci rozebírat skutečné výhody a nevýhody populárních frameworků a knihoven – na základě reálných zkušeností z produkce, ne teoretických přínosů.

Protože nakonec je nejlepší ta technologie, která vám pomáhá efektivně stavět skvělé produkty – ne ta s nejpůsobivějším demem.
